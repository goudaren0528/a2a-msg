# IM bounded clock guard (core integration)

`createImClockGuard({ db, clock = Date.now })` returns `{ runRead(fn), runWrite(fn), current() }`. Core factories now accept `{ db, clock, timeGuard }` and bind the guard on the same connection; pass the **same exact clock function reference** to every factory (including ACL). Repeated binding returns the same guard and a different clock on that connection is rejected. If passing `timeGuard`, pass `clock` too when it is not `Date.now`; identity must equal the canonical bound guard. Never accept a guard through HTTP input. All callbacks are strictly synchronous. `current()` is available only inside an active guard scope, returns the operation's fixed timestamp, and otherwise fails closed (`CLOCK_UNSAFE`). Legacy `readImClock` and `observeImClock` only read the active guarded snapshot, never sample or persist time on their own.

An outer `runRead` commits a clock observation in its own `BEGIN IMMEDIATE` transaction, then pins a SQLite read transaction and verifies the persisted floor before invoking the callback. Its nested reads reuse one timestamp and snapshot. The read callback must perform reads only, not directly mutate the database or control transactions; the guard forbids upgrading via `runWrite` but cannot intercept raw SQL. A concurrent connection may advance time after the snapshot is pinned; the read operation remains valid against the **earlier snapshot**, not against newly committed state. An outer `runWrite` commits the clock observation **before** opening a separate `BEGIN IMMEDIATE` business transaction; it rechecks the stored floor under the business lock before invoking the callback. If another connection advanced it in between, it retries at most three times; continuing competition returns retryable `STORAGE_UNAVAILABLE`. `runWrite` in any existing guard scope rejects `INVALID_REQUEST` (including write-to-write and read-to-write); reads inside a write scope reuse the fixed timestamp. This guarantees message service post-commit callbacks cannot fire before an outer write commits. Callback errors and thenables roll back the business transaction, never the previously committed clock observation. External transactions without a guard scope are rejected rather than implicitly nesting.

Unsafe, thrown, or backward clock samples fail `CLOCK_UNSAFE` without leaking clock exceptions. Once sampled, the process high-water mark remains even on anchor UPDATE/COMMIT failure. Failed storage locks return retryable `STORAGE_UNAVAILABLE` without invoking callbacks. Reads and writes require SQLite `PRAGMA synchronous` FULL (2) or EXTRA (3); the guard never changes this configuration. For a power-loss durability claim configure a suitable persistent SQLite filesystem, journal/WAL and FULL/EXTRA synchronization before use; `:memory:` permits functional tests but not power-loss recovery. A replaced/restored older database backup or writes outside the guard can violate the monotonic-clock guarantee; this guard cannot detect restores to an earlier backup after process restart. No deployment or production migration is performed here.

Migration `previewLegacyBindings` intentionally uses trusted synchronous administrator authorization and a static read-only snapshot, without a guard/time-based expiry decision: it does not mutate even the clock metadata. All other migration operations, including `getWriteMode`, use a guard scope. A failed guarded business write may independently advance `im_clock`; business state, sequences, keys and audit changes roll back together. Message notifications happen only after the write scope has committed and exited and are best-effort.
