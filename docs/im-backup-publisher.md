# Trusted local backup publication coordinator (isolated)

Use `createTrustedBackupServices({ db, dir, authority, clock })` from `backup-registry.js`; it returns `{ publisher, registry }` without exposing its private registry writer, backup primitive, controlled directory or arbitrary artifact/hash registration. The registry facade offers only read/management operations. `publisher.publish({ adminContext, approvalId })` is the **only supported** publication writer. There is no HTTP surface or deployment integration. `authority.authorizeAdmin(adminContext)` must return synchronous literal `true`, while a trusted authorization adapter must bind `publicationActors(adminContext)` to approved `executorActorId` and `backupApproverId`. The stock `createAdminAuthority` authenticates a secret but does not produce actor identities; configure the adapter only in a protected management process. Do not log, persist or pass admin secrets via arguments.

The publisher reads the source v2 identity from the current DB, registers/checks immutable registry generation 1, chooses a controlled artifact name, invokes the actual `backup.backup` with the same admin context, and requires strictly `durable` success. It calls actual `backup.verify()` for content/integrity/foreign keys/schema/hash, opens the copy read-only and compares its instance ID and `createdAt` with the source, rechecks live source identity after asynchronous backup and registry generation, then registers computed hashes and trusted actor fields through its closure-held writer. Submitted `sourceId`, `instanceId`, paths, file hashes, booleans or purported provenance are not accepted as authority. The writer additionally checks manifest source ID, copied DB identity and actual content verification as defense in depth, **not** as independent provenance proof. The return indicates `publicationState: 'published'` and `provenance: 'registry-recorded'` only on successful registration.

`backup.verify()` verifies content but does not attest origin. The registry records controlled publication but does not replace fresh verification. **This change closes the public generic registry writer bypass**, not the full provenance chain. Tests construct historically acceptable field payloads but do not execute an old-version writer or dynamically reproduce its exploit. The current factory publisher ignores submitted artifact/hash/ID/source fields; on Windows real strict backup fails before the publication path can be exercised, so its Windows logic checks do not substitute for Unix strict E2E. A publisher-level copy-substitution test checks actual B snapshot content (including both source-label variants) and confirms the identity rejection before writer calls. Another test tampers with business foreign keys, recomputes the file hash and updates the manifest; real `backup.verify()` still refuses the content. The source may change during asynchronous backup: identity is re-read before registration, but this is not a cross-process transactional lock. A failed result can leave artifacts or uncertain disk entries requiring reconciliation. A process with equivalent OS write privileges can still forge records; the trust boundary is OS protection and a trusted management process, not cryptographic provenance.

The `platform` override is solely a test capability; it does not verify real ACLs or durability. On Windows the native registry fails closed, while native strict backup can fail with `BACKUP_DURABILITY_UNAVAILABLE`; degraded/best-effort output is not publishable. Unix native strict E2E requires protected 0600 secret files and 0700 directories and a filesystem that can fsync directories. A Unix-native E2E test is written and skipped on Windows: Windows test results do **not** constitute acceptance of Unix strict E2E. During this prototype, use only a **new, protected registry with no legacy records**. Records written by the old public writer are **not automatically trusted** after upgrade; do not use them as provenance—reissue fresh backups through the trusted publisher after independent review/reconciliation.

Outstanding: cross-process revocation/use serialization; migration runner integration with real identity and resolver; full validation outside the write lock and integration tests for lock-external/transaction-internal responsibilities. `migration-runner.js:119–120` **already checks expiry inside its transaction**; remaining time work is shared guard reuse and anti-clock-rollback semantics, not adding the existing expiry check again. Neither this isolated coordinator nor passing tests closes the complete provenance chain or releases **C gate**. No production-readiness claim is made.
