# IM HTTP adapter (isolated, not mounted)

The `/messages` 16 MiB allowance accommodates encoded attachments; without a truthy `attachment` field, the full JSON request is additionally capped at maxBodyBytes (≤64 KiB) before service invocation. Core normalization enforces decoded attachment validity and its ≤10 MiB limit. Malformed attachment requests are still bounded to 16 MiB before parsing.

`tests/fixtures/im-tls/localhost-test-only.{crt,key}` is a **public test-only self-signed certificate and private key** with SAN `DNS:localhost,IP:127.0.0.1`. It contains no application credentials and must not be deployed. Isolated HTTPS tests explicitly trust this certificate as CA, retain certificate/hostname verification, and reject an untrusted CA and mismatched hostname. This demonstrates localhost behavior only, not internet deployment readiness.

Download performance/security: `messages.getAttachment` performs the initial authenticated BLOB retrieval and full SHA-256 check once. The handler subsequently uses `acl.assertAttachmentAccess(principal,attachmentId)` for each 64 KiB write/backpressure resumption; this rechecks branded credential and current contact without selecting the BLOB again. A 10 MiB HTTP test observes exactly one `SELECT * FROM im_attachments` for an authorized download and zero for an unauthorized request. A contact or credential revoked mid-transfer terminates the response before later writes (already emitted bytes remain irrevocable). `close()` aborts an active download but does not close the external HTTP listener. The 30-second request timeout is not covered by a timed test; its timer is cleared on exit and default policy is not configurable by untrusted requests.

`createImHandler({auth,acl,messages,delivery,policy})` returns `{handle(req,res),close()}`. `handle` resolves `false` without touching responses outside the exact `/api/v1` boundary; an application must explicitly mount it and handle `false` itself. It does not start a server, open a database, register admin endpoints, or install legacy fallbacks. Missing/invalid explicit policy disables the adapter. Policy is parsed and snapshotted at creation. A valid enabled policy must select `direct-tls` (actual encrypted socket, HTTPS configured URL) or `local-test` (both socket ends loopback, explicit loopback URL). Forwarded headers never establish TLS or loopback; **public proxy-to-localhost is unsupported**. No insecure production override. `close` rejects new IM work, clears rate state and destroys only in-progress IM responses, not external listener/socket ownership.

All handled responses include `Cache-Control: no-store` and generated `X-Request-Id`; errors have `{error:{code,message,retryable},requestId}` with fixed `ImError` text. Unexpected exceptions are `STORAGE_UNAVAILABLE`, never internal exception details. 429 includes `Retry-After: 60`. No logs or credential-bearing rate keys. Body reads cap at configured maxBodyBytes (≤64 KiB), except `/messages` maxFileBodyBytes (≤16 MiB); attachments remain capped by service policy ≤10 MiB. JSON requires exact `application/json`, bounded streaming before parsing, and POST schemas reject unknown fields. GET has no body. No client sender/principal override: only single canonical `Authorization: Bearer <credential>` goes to `auth.authenticate`; `/me` returns only `{agentId}` (no credential ID or display name). Query keys may occur once only; unknown keys fail. Receiver proof uses unique `X-A2A-Instance-Id` and `X-A2A-Generation`, never a query secret. Duplicate sensitive raw headers fail. Unknown IM routes (including `/api/v1/events`) return `RESOURCE_NOT_FOUND` and never map to legacy unread-events.

Routes (all request IDs in errors; success directly serializes safe service DTO): GET `/me`, `/contacts?after&limit`, `/conversations?after&limit`; POST `/conversations` `{peerAgentId}`; GET `/conversations/:id/messages?after&limit`; POST `/messages` exact `normalizeMessageRequest` raw shape (201 new, 200 replay); GET `/sends/:clientMessageId`, `/messages/:id`, `/attachments/:id`; POST `/messages/:id/read` `{}`; POST `/receiver/lease` `{instanceId,requestId}`, `/receiver/lease/renew` and `/receiver/lease/release` `{instanceId,generation}`; GET `/sync?after&streamEpoch&limit` with receiver proof headers; POST `/acks` `{instanceId,generation,messageIds}`. All statuses for domain errors come from `ImError` in `docs/im-api-contract.md`. Attachment downloads are octet-stream, `nosniff`, RFC 5987 encoded filename, validated by the message service and rechecked via core `acl.assertAttachmentAccess(principal, attachmentId)` (which revalidates auth and contact) before every 64 KiB write and after a stalled write. Revocation after headers destroys the response, not a second JSON response. Already transmitted bytes cannot be recalled.

Limitations/host responsibilities: Node HTTP server must enforce `maxHeaderSize ≤8192`, `maxHeadersCount`, `headersTimeout` and `requestTimeout` before handler dispatch (the handler additionally counts up to 8192 raw header bytes). Configure server-level socket/connection concurrency limits; adapter counts concurrently handled IM responses up to `maxConnections` and has bounded per-IP 60-second request counters (eviction at 4× maxConnections, at most 4096; eviction can relax per-IP limits under IP churn, so host-level rate limiting is also required). Adapter timeout is 30 seconds and destroys the active response. The adapter cannot revoke bytes already sent or enforce identity-based quotas before authentication. SSE and deployment integration are out of scope. A terminating TLS proxy is not supported; use direct TLS to this server, or explicitly isolated loopback-only test mode.
