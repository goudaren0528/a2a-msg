# IM v1 SQLite storage contract (implementation foundation only)

`src/im/schema.js` exports `IM_SCHEMA_VERSION = 1`, `migrateImSchema(db, { expectedVersion = 1 } = {})` and `assertImSchema(db)`. `src/im/transaction.js` exports `withImmediateTransaction(db, fn)`. These modules do **not** open a database, initialize the legacy database, run automatically on import, migrate legacy members, expose HTTP routes, or enable IM writing. Supply a Node 24 `node:sqlite` `DatabaseSync` connection with `PRAGMA foreign_keys = ON` outside any transaction. Back up and preview a real database under separately approved operations before invoking migration; tests use isolated in-memory connections only.

## Immutable v1 schema

All names below are exact snake_case. `TEXT` identifiers are nonempty and at most 255 characters unless stated otherwise; the service/contracts layer owns ID format and authorization. All timestamps are integer milliseconds since Unix epoch, `0..9007199254740991` (nullable where marked), not ISO strings. All future writes must fit JS safe integers. SQLite checks guard basic storage shape, not full protocol validation. No `ON DELETE CASCADE` applies to historical messages. `im_` tables do not reference or alter legacy `members`, `messages`, `attachments`, `tokens`, or legacy read state.

| `im_conversations` | `conversation_id TEXT PRIMARY KEY`, ordered `agent_low`, `agent_high` TEXT NOT NULL FK agents, `created_at INTEGER NOT NULL`, unique ordered pair. |

## Migration and transaction semantics

The v1 DDL manifest comprises exactly the listed tables and six named indexes; SQLite automatically generated indexes are excluded. Manifest canonicalization trims and collapses SQL whitespace and sorts `[type,name,tbl_name,sql]` tuples by object name; SHA-256 of its JSON representation is `migration_checksum`. `assertImSchema` compares the **actual `sqlite_master` SQL** and objects (including unexpected `im_*` triggers/views) against the immutable manifest, then validates marker row, singleton row counts and IM foreign-key integrity. Canonicalization tolerates whitespace changes only; altered columns, constraints, indexes, or triggers fail closed. A missing/unknown/counterfeit marker or any partial experimental `im_*` schema is never silently adopted. Future version changes require a new reviewed migration, not changes to v1 manifest. Call `assertImSchema` before dependent operations; do not interpret a mismatch as permission to rebuild or overwrite.

`migrateImSchema` checks FK enforcement and the requested version, obtains `BEGIN IMMEDIATE`, probes for any `im_*` objects, initializes all objects plus marker and singleton rows as one atomic transaction only if absent, then verifies. Repeated matching calls are idempotent. Errors roll back, leaving legacy data untouched. This is **schema only**, not a live rollout or legacy-member import. For an existing live database, separately authorize backup/recovery rehearsal, preview, maintenance window and new-write gate before migration.

`withImmediateTransaction(db, fn)` synchronously begins `IMMEDIATE`, commits on success, rolls back on failure and rethrows the original error. It rejects nested or already-active transactions and async-function callbacks before BEGIN (`IM_TRANSACTION_INVALID`); a returned thenable is rejected and rolled back. It cannot undo asynchronous external side effects started inside a synchronous callback: do not initiate them there. A rollback failure is attached as a cause when possible without replacing the original error. The transaction helper does not log bodies. Storage mismatch errors use `IM_SCHEMA_MISMATCH`; map these fixed codes to outward-facing protocol errors in the later integration layer without exposing raw SQL or secrets.
