# Internal protected backup registration storage (isolated module)

`createBackupRegistry({ dir, authority, clock })` uses a **pre-existing private local directory** owned by the executing OS user (0700); create a private `artifacts/` subdirectory (0700) first. It performs no HTTP, database migration or deployment. It is not wired into the migration runner. The trusted administrator process supplies `instanceId` from its managed schema identity, not from a client's assertion, and `dbLocation` from its own DB configuration. `registerInstance({ instanceId, dbLocation, adminContext })` establishes immutable generation 1. Subsequent generations require a separate reviewed lifecycle; this module deliberately does not silently rotate identity. `getInstance()` returns only ID and generation, never the DB location.

The optional `platform` capability (`privateDirectory`, `protectedPath`, `checkOpened`, `syncDirectory`) is **test-only injection** to exercise registration logic across platforms with a deterministic trusted-platform double. Production callers must omit it: the real default checks protected ownership/modes, symlinks and opened-file identity, and fsyncs the directory or fails closed. The double neither verifies real ACLs nor supplies real crash durability; passing its tests is not Windows safety validation. Windows still requires a supported environment and independent verification of real ACL/reparse and directory-fsync semantics before any production use.

Only the trusted managed backup publication process should call `registerPublishedBackup(...)`, and only **after** its own backup `verify()` succeeded and it copied/published its output inside the controlled `artifacts/` directory. Required fields: `instanceId`, `registrationGeneration`, `backupId`, SHA-256 `fileHash`, `schemaVersion`, SHA-256 `schemaChecksum`, `completedAt`, `executorActorId`, `backupApprovalId`, `backupApproverId`, `toolVersion`, relative `artifactReference` (`artifacts/<name>`), SHA-256 `manifestHash`, and `adminContext`. The module checks artifact and manifest hashes, protected file ownership/mode, and selected manifest fields before publishing. It does **not** invoke SQLite integrity/schema verification itself. `publicationState: 'published'` is recorded on successful publication, not accepted from the caller. The authorization check accepts only a synchronous literal `authority.authorizeAdmin(adminContext) === true`; thrown errors, missing authority, promises and `{admin:true}` fail closed. Secrets are never persisted, returned, put into process arguments or logged.

**Not a trusted provenance gate.** `registerPublishedBackup` does not read the instance identity within the copied database, does not run a real SQLite/content `verify()`, and cannot prove the backup's source. A trusted publisher/coordination flow (real backup → copied database instance-ID check → strict artifact durability → content verification → registration) and an independently reviewed migration gate remain to be implemented. Trust derives from OS access control and the trusted management process, not self-declared JSON fields. A process holding that same OS privilege can write convincing JSON; a test double marking a direct-write path untrusted does **not** establish otherwise.

Registry files are private (0600), individually fsynced and hard-linked from a temporary file to an immutable final name (atomic no-replace); the registry directory is fsynced before success. A failed directory fsync returns `REGISTRY_DURABILITY_UNAVAILABLE` if rollback is confirmed, or `REGISTRY_CLEANUP_INCOMPLETE` if rollback durability cannot be confirmed—**never degraded success**. Disk corruption, crash between link and directory fsync, external filesystem interference or cleanup failure requires operator reconciliation: absence of a success response does not prove absence of an on-disk entry. No best-effort publication setting exists. This is a local OS account/ACL trust boundary, **not** a signed attestation: a process with the same OS write privilege can forge records and artifacts. JSON booleans and hashes do not authenticate origin. An unprivileged direct-write attempt should be blocked by filesystem permissions, not by parsing a `published` field. Do not expose the registry directory or admin credential to the user-facing service.

Records have exact versioned reader schemas (`recordVersion: 1`); unexpected fields, invalid types and malformed revocations fail with `REGISTRY_UNTRUSTED_RECORD`. Publication removes its pending hard link before directory sync. A crash before that sync may leave an orphan pending entry, a final entry, or both: **none is automatically recognized as newly successful provenance**. Stop writers, inspect the protected directory and managed backup/approval evidence, and reconcile manually before any retry. Failed rollback attempts to fsync the registry directory after unlink; if this cannot be confirmed, `REGISTRY_CLEANUP_INCOMPLETE` reports uncertain durability, not success. Revoked cleanup syncs the changed `artifacts/` directory; a failure after the first leaf deletion retains revocation and allows a controlled retry that removes remaining leaves. If that directory sync fails, deletion durability is uncertain and requires manual reconciliation.

`resolveForMigration({ backupId, expected: { instanceId, registrationGeneration, fileHash, schemaVersion, schemaChecksum } })` rejects absent, revoked, untrusted or mismatched registrations; it rechecks controlled artifact and manifest hashes. This provenance gate is separate from backup `verify()`, which verifies **content** (SQLite integrity, foreign keys, schema and file hash) and must also succeed before migration. A verified file alone is not publication evidence; a registry record alone is not a fresh SQLite content verification. `dbLocation` does not enter the public resolution response.

`beginUse(backupId)` returns a unique-token end handle; repeated `handle.end()` is idempotent and cannot release another handle. `drain()` waits until all real handles have been released. No public `endUse(backupId)` exists. `revokeBackup({ backupId, adminContext })` creates a no-replace revocation marker; `cleanupBackup({ backupId, adminContext })` removes artifact and manifest only after revocation. Both reject in-process active use. These handles guard only **this registry object in this process**: they do not lock other processes, direct filesystem mutations or a different registry object. A caller should resolve and begin use in its trusted isolated operation before working with the artifact, end in `finally`, and externally coordinate all readers/writers and deletion. This module must not be treated as a cross-process lease or race-free TOCTOU barrier.

Windows is **unsupported/fail closed**: Node's portable APIs do not verify owner ACLs or reparse-point ancestry adequately, and directory fsync may be unavailable. Do not inject the test platform to avoid this refusal. On Unix, protected leaf files must have one hard link, be owned by the effective user, and have no group/other permissions; the registry and artifacts directories require private ownership/mode. Every ancestor must have a trusted owner (effective user or system root), not merely non-writable permission bits; sticky temporary parents require trusted ownership too. This is not an adversarial concurrent filesystem-mutation defense. On a filesystem that does not durably fsync directories, registration fails closed rather than claiming crash-safe provenance. Backups may exceed the keystore's 4096-byte secret limit; only registry JSON is bounded to 1 MiB, and artifact hashing is streamed. Real Unix semantics tests must run on a supported Unix host; Windows fail-closed is the correct result. This isolated module and tests are not production-readiness evidence.
