# Protected backup registry (Lane A prototype)

`createTrustedBackupServices({ db, dir, authority, clock })` returns frozen `{ publisher, registry }`; the private writer and backup primitive are not exposed. `createBackupRegistry({ dir, authority, clock })` returns only the registry facade. Both require a pre-existing private Unix directory and `artifacts/`; Windows native protection is unsupported and fails closed, including when a `platform` option is supplied. NFS/SMB are not certified. Only a trusted local administrator/process with exclusive control of the directory is in scope; OS-equivalent adversaries can forge content.

The registry creates `coordination.sqlite` exclusively with mode 0600 and a separate SQLite connection. It never deletes/recreates an existing coordination file. Every registry operation uses `BEGIN IMMEDIATE` with `busy_timeout=0`; contention is `REGISTRY_BUSY` (retryable). Locks cover record checks, durable publication, revocation and artifact cleanup; callback use holds the lock through synchronous callback completion. SQLite OS locks release on process death. Order is registry lock before live DB transaction. Do not run the full backup verification inside a live database write transaction. Filesystem fsync, no-replace publication and rollback remain required; a release failure is `REGISTRY_LOCK_RELEASE_FAILED`, and a callback may already have committed: do not compensate by deleting a backup or asserting no commit.

On Unix, closing any raw file descriptor opened on the coordination inode in the **same process** can release all its POSIX record locks, including a lock held by another SQLite connection. Creation-only fd writes/fsync/close finish before the file is eligible for locking; subsequent validation uses non-opening `lstat`-based owner/mode/type/nlink and directory checks with inode comparisons. SQLite-managed read-only probes may open/close their own connections. Managed facades never raw-open/close the coordination inode while a lock can exist; unrelated same-privilege code that does so is outside the trusted-process boundary.

Only exact `recordVersion: 2` instance and publication records are eligible. Both bind the DB's `instanceId` and numeric safe-integer `createdAt` (`instanceCreatedAt` in registry), with `registrationGeneration: 1`. Legacy v1 records are rejected without conversion or trust flag; republish into a fresh protected directory following independent reconciliation. No IM schema version changes are implied.

`registry.withDiscoveredBackup({ backupId, expectedIdentity: { instanceId, instanceCreatedAt, registrationGeneration } }, callback)` discovers registered evidence using only the backup ID and independently read live identity (numeric generation `1`). Under one coordinator lock it verifies the private v2 publication and instance records, absence of revocation, controlled artifact and manifest hashes, manifest/publication identity, real backup integrity/foreign-key/schema/hash checks, and copied DB identity **before** the synchronous callback. It yields frozen `{ backupId, instanceId, instanceCreatedAt, registrationGeneration, fileHash, manifestHash, schemaVersion, schemaChecksum, recheck }`; discovery is not approval or authentication. The caller must not derive identity from the submitted request. No caller artifact path or writer is exposed.

`registry.withVerifiedBackup({ backupId, expected: { instanceId, instanceCreatedAt, registrationGeneration, fileHash, manifestHash, schemaVersion, schemaChecksum } }, callback)` requires **all** expected fields with valid types/formats; missing `manifestHash` (or any other approved field) is rejected, never silently discovered. It performs the same full physical verification. `recheck()` performs **metadata-only** instance/publication/revocation comparisons against every originally verified field under the held lock, without file hashing, copy opening or SQLite integrity verification; it rejects use after the callback exits. Inputs are copied before callback invocation, so callback mutation cannot change the checked target. Known async functions are rejected before invocation; other callbacks returning thenables are rejected afterward with `REGISTRY_ASYNC_CALLBACK`. Trusted synchronous callbacks are not sandboxed: asynchronous side effects started by an ordinary callback cannot be canceled. `resolveForMigration` also requires all expected fields but does not replace either full verified callback scope; it performs hashes rather than complete verification. `status`, `drain` and the old `beginUse` Map token were removed because they could not express cross-process use.

An initialization crash after exclusive file creation but before durable version establishment leaves a failed-closed coordination file requiring **manual offline reconciliation**; it is never automatically unlinked or recreated. Directory-sync and lock-release failures may leave uncertain durable state.

Migration runner/factory integration is deferred to Lane C. No production or deployment readiness is asserted.
