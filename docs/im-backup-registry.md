# Internal protected backup registration storage (isolated)

`createBackupRegistry({ dir, authority, clock })` returns only the public reader/management facade: `getInstance`, `resolveForMigration`, `beginUse`, `revokeBackup`, `cleanupBackup`, `status`, `drain`. It has **no `registerInstance` or `registerPublishedBackup`**, no artifact directory accessor, and no generic artifact/hash publication API. `createTrustedBackupServices({ db, dir, authority, platform, clock })` privately creates a writer and a real `createImBackup`, returns only `{ publisher, registry }`, and makes `publisher.publish()` the only supported publication route. No HTTP endpoint or migration runner is added. The registry directory and `artifacts/` must already exist, private (0700), under a trusted OS user.

The private writer checks the manifest source ID, opens the copied SQLite file read-only for identity validation, invokes real `backup.verify()`, checks artifact and manifest hashes and protected file ownership/mode. These writer checks are **defense in depth, not an alternative provenance mechanism**. **Only the public generic registry writer bypass is closed.** The prior public `registerPublishedBackup` checked fields and hashes but not copied SQLite validity/identity or manifest source; historical payload tests illustrate these field constraints and prove the **new interface is unreachable**, not a dynamic old-version exploit replay. The new facade cannot submit arbitrary files or relabeled backups. A privileged process capable of editing registry files remains outside this capability isolation; the boundary is OS permissions **and** a trusted management process, not a cryptographic signature. Prototype rollout requires a **new protected registry without legacy records**; older records are not automatically trusted and require fresh issuance through the trusted publisher after independent reconciliation.

Record publication uses fsynced private (0600) files, hard-link atomic no-replace final names, and directory fsync. Repeat revocation is tested to reject an existing marker. The public publisher generates its own random backup ID: the test passes a duplicate caller ID and checks that a pre-existing record is untouched, **not** that the private writer was exercised with a duplicate generated ID. Direct duplicate-publication and two-process race behavior are not independently exercised by these tests. On failure rollback attempts to persist removal; `REGISTRY_DURABILITY_UNAVAILABLE` or `REGISTRY_CLEANUP_INCOMPLETE` expresses uncertain durability. No failed response proves an absent disk entry: reconcile after crash, disk fault or cleanup error. `resolveForMigration({ backupId, expected: { instanceId, registrationGeneration, fileHash, schemaVersion, schemaChecksum } })` refuses missing, untrusted, revoked or mismatched entries and rehashes controlled artifacts. A registry record is not a fresh content verification. Immutable generation 1 is registered only by the trusted publisher; no implicit generation rollover exists.

`beginUse(backupId)` returns a unique idempotent `end()` handle; `drain()` waits for this object’s active handles. Authorized `revokeBackup` creates an immutable no-replace revocation marker; `cleanupBackup` requires revocation and refuses active use. These guards work only within **one registry object and process**, not across processes or direct filesystem mutations. Cross-process use/revocation serialization remains unimplemented.

`platform` (`privateDirectory`, `protectedPath`, `checkOpened`, `syncDirectory`) is **test-only**. The real default enforces Unix owner/mode, rejects symlinks, checks opened-file identity and directory fsync or fails closed. Windows has unverified ACL/reparse and directory fsync semantics and the native registry refuses operation (`REGISTRY_PERMISSION_UNVERIFIED`); injecting a test double cannot establish Unix strict E2E or production safety. Cross-process use/revocation serialization is unimplemented. The migration runner needs real identity/resolver wiring, full validation outside locks, integration tests for lock-external versus transaction-internal responsibilities and shared guard/anti-clock-rollback time semantics. `migration-runner.js:119–120` already checks expiry within its transaction; it is not a missing check. **C gate remains closed**. This module is not deployment or production-readiness evidence.
