# IM legacy binding and write-mode control (isolated implementation)

This module is **not** a production migration runner, authentication provider, service activation switch, or deployment procedure. It never copies legacy messages, attachments, tokens, read state, sender access, or `reply_to`, and never creates an IM conversation. A binding is `legacy_ip` metadata only: an IM credential does **not** confer access to old messages or attachments. Legacy and IM endpoints must remain separate and enforce their respective authorization independently.

Before any real rollout, separately approve a recoverable backup and restore rehearsal, verify the supported schema and policy, establish a trusted administrator authentication boundary, and review every mapping. The lower-level migration tests include isolated in-memory SQLite; the separate trusted local runner also exercises file-backed v2 identity and protected Unix backup registry (see `im-migration-runner.md`). Neither constitutes a live migration rehearsal. No retention durations, production endpoints, or legacy API cutoff are chosen here.

## API

`createImMigration({ db, clock = Date.now, authorizeAdmin })` returns:

- `previewLegacyBindings(proposedBindings, adminContext)` (read-only): `proposedBindings` is a nonempty array (maximum 1000) of exact `{ legacyMember, agentId }` pairs; no unknown keys or duplicate member/agent. The administrator independently supplies each mapping; matching display names are never used. Every legacy member must exist and not be revoked, every target agent must be active and not revoked, and neither side may already have a binding. Returns `{ previewId, sourceFingerprint, proposedBindings }` with sorted canonical mapping. Preview does not write `im_migration_runs`, `im_clock`, or audit. ID is a deterministic UUID-shaped digest prefix and fingerprint is SHA-256 over a version tag, mapping, member existence/revocation, agent status/revocation and both existing-binding lookups. No messages or attachments contribute; new legacy messages do not stale the preview. A changed identity/binding state does.
- `commitLegacyBindings({ previewId, sourceFingerprint, approvedBindings, approvalRef }, adminContext)`: the external authenticated approval workflow must review the **entire canonical list** and bind its approval reference to that exact list and fingerprint. No preview is persisted: the transaction recomputes the fingerprint from the approved list and current source state and compares both submitted values. An arbitrary client-provided digest alone is **not evidence of administrator approval**; authorization and approval verification are integration responsibilities. The call atomically creates one completed `im_migration_runs` row, approved `im_legacy_bindings` rows (source `legacy_ip`), and one safe aggregate `im_audit` row. An exact completed batch retry by the same trusted actor with the same approval reference succeeds without further writes; changed mapping, actor, approval or current binding rejects. Other failures roll back all rows and observed clock time. The run ID is derived from the preview hash and satisfies the schema's UUID-shaped ID check.
- `setImWriteMode({ mode, reason, policy? }, adminContext)`: explicit administrator action; `mode` is `paused` or `enabled`. Enabling **requires** a complete `{ enabled: true, writeMode: 'enabled', transport, retention, lease, ... }` accepted by the actual `parseImConfig` function. `policy` is not permitted for pause. Each operation atomically updates `im_settings`, observes safe time, and appends a metadata-only audit record. It does not start listeners or mutate legacy tables/messages, IM messages, send keys, ACK state or leases. The caller must integrate and enforce the persisted write mode at every new IM write entry point; this module does not enforce those entry points.
- `getWriteMode()` reads the `im_settings` singleton via its indexed primary key; schema and foreign-key validation occur once at factory construction, not per mode lookup; it does not authenticate a user. Restrict its exposure at the caller boundary if mode visibility is sensitive.

Every administrator action requires a **synchronous trusted** `authorizeAdmin(adminContext)` callback returning a safe nonempty actor ID string (or `{ actorId }`). Missing callback, rejected authorization, promise, boolean or echoing the context fails closed with `ImError('OPERATION_FORBIDDEN')`. Never implement this callback by simply trusting `adminContext.admin === true` or by echoing untrusted caller fields. The callback must perform real administrator authentication and the integration must independently validate that the approval reference belongs to an approved mapping. Authentication is not supplied by this module. Inputs with unknown fields fail as `INVALID_REQUEST`; conflicting mappings/stale previews return `IDEMPOTENCY_CONFLICT`; unsafe time returns `CLOCK_UNSAFE`; incomplete activation policy returns `POLICY_NOT_CONFIGURED`. Storage mismatch errors from `assertImSchema` remain `IM_SCHEMA_MISMATCH`. No raw SQL, bodies, attachments or credential content are put in fingerprints or audit by the module. Keep `reason`, `approvalRef` and actor identifiers non-sensitive operator metadata.

`setImWriteMode` persists **only the mode**, not the supplied policy. A prior successful enable does not make policy durable: the integration must supply, validate and enforce its current runtime policy again before accepting new writes. `getWriteMode() === 'enabled'` alone never bypasses transport, retention, lease or other runtime policy requirements.

## Safe rollback / maintenance

Use an explicitly authenticated `setImWriteMode({ mode: 'paused', reason: 'maintenance' }, adminContext)` to stop **new** IM writes at integrated entry points. Continue safe read-only access when separately authorized, or stop the new protocol completely while preserving IM messages, idempotency keys, deliveries/ACKs, leases, and legacy data. Do not DROP any tables, remove legacy tokens as part of migration, or restore an old DB backup over messages accepted after that backup. Evaluate recovery with a separately approved plan; a paused gate is not a database restore. Nothing here bypasses the legacy recipient's historical access rules.
