# IM client journal (isolated local lane)

`createImJournal({db,centerId,agentId})` exports a frozen **synchronous** API. `migrateImJournal(db)` is also exported; the factory calls it idempotently. Supply an already-open Node `DatabaseSync` configured by the installer with foreign keys and `synchronous=FULL`, on a protected persistent filesystem. Neither export opens a path, performs network/model calls, or accesses central `im_*` tables. The journal owns only `im_client_meta`, `im_client_outgoing`, `im_client_received`, `im_client_receiver`. Schema version/checksum and actual DDL are checked at creation; unknown versions/mismatches fail `IM_SCHEMA_MISMATCH` without deleting or upgrading records. No retention or automatic purge exists. Database/attachment ACL, encrypted storage if required, backup and disk durability are installation responsibilities. Message text and outgoing base64 payload are **business data** intentionally saved locally; no tokens, credentials or secrets should be supplied or stored.

`centerId` is a trusted configured canonical HTTPS origin (optionally final `/`, no credentials, path, query or fragment), not a value copied from a message. `agentId` is a stable UUID. Every row is keyed by normalized center origin and agent UUID; client message IDs cannot collide across these scopes. The installer must not silently switch these identities. Timestamps are server `acceptedAt` or local wall-clock record times; local time does not invoke the central clock guard and is not authority for server leases.

## Outgoing

- `stageOutgoing(rawRequest)` → `{clientMessageId,fingerprint,request,createdAt,messageId,acceptedAt}`. Runs the real `normalizeMessageRequest` (10 MiB max) and `fingerprintMessage`, then saves a complete normalized replayable HTTP request JSON, including canonical attachment base64. Unknown raw fields, invalid digest, oversized file, self-recipient etc. fail closed. Same scoped key/hash returns the existing record, different hash raises `IDEMPOTENCY_CONFLICT`. **Always reuse `request.clientMessageId`** after timeout or restart, never mint a replacement for a staged send.
- `getOutgoing(clientMessageId)` → record or `null`. `listPendingOutgoing({limit?})` → at most 100 lightweight `{clientMessageId,createdAt}` items ordered oldest first (default 20); call `getOutgoing` individually to read the large payload. Pending includes response-lost cases until explicitly accepted. This list is not an unbounded bulk body loader.
- `markAccepted(clientMessageId,{messageId,acceptedAt})` → updated record. Only a locally staged scoped key may be marked; existing different mapping/timestamp conflicts. **Caller must independently verify the authenticated server result** belongs to this agent and staged request (e.g. `clientMessageId`, sender/recipient/conversation and message DTO), from POST `/messages` or GET `/sends/:clientMessageId`; this method cannot authenticate a bare pair of identifiers or prove a server send. On lost response, query the send key first, then retry the *stored* identical request while the server's documented idempotency window is live; expiration is not permission to invent a new key.

## Receiving and ACK

- `recordReceived({streamEpoch,seq,message,attachmentReceipt?})` → `{streamEpoch,seq,message,attachmentReceipt,recordedAt,acked}`. `message` is the exact validated `/sync` item DTO, not arbitrary raw JSON: `{messageId,conversationId,senderAgentId,recipientAgentId,clientMessageId,title,text,inReplyTo,correlation,acceptedAt,attachment}`, where attachment is `null` or `{attachmentId,name,mime,size,sha256}`. `recipientAgentId` must equal the configured agent. Do not pass historical message DTOs with `deliveredAt/readAt` or bytes/base64. Persist only metadata, body and a receipt, never attachment bytes. When attachment exists, receipt is required: `{path,sha256,size}` matching metadata; without attachment it must be omitted/null. **The caller must already have safely saved and SHA-256/size-verified the file; the journal does not access disk and cannot establish that a caller-provided path was verified.** Same epoch/sequence/message/receipt is idempotent; changed duplicates conflict. A different epoch fails `CURSOR_RESET_REQUIRED` rather than silently discarding an old stream. Epoch reset/reconciliation requires an explicit future client policy, not a hidden journal state transition.
- `getReceived(messageId)` → record or `null`; `listPendingAcks({limit?})` → at most 100 `{streamEpoch,seq,messageId}` (default 20). These support replay after crash, including already saved attachment metadata. A duplicate must be correlated with the stable message/attachment IDs and its persisted receipt; do not write a second file.
- `markAcked({messageIds,ackedThrough,streamEpoch})` → `{streamEpoch,cursor}`. Supply only a successful authenticated `/acks` result and IDs submitted in that ACK (1–100 unique UUIDs). In one local transaction every ID must have a durable scoped receipt, otherwise `DELIVERY_REQUIRED` and nothing changes. `ackedThrough` is a server response watermark, **not** an instruction to mark every earlier local row ACKed. Only named IDs become ACKed. `cursor` advances only across consecutive locally durable ACKed sequences from the previous cursor and never past the supplied watermark; gaps remain pending. The server's `/sync?after=` accepts positions up to its own `ackedThrough`, so the client must reconcile against the actual server stream and never use a fabricated higher local cursor to skip messages. No server ACK should be sent before local records and attachment receipts are durable.

## Lease cache

`setLease({instanceId,generation,expiresAt,streamEpoch?})` → cached lease plus cursor; `getLease()` → that cache or `null`. Generation may not decrease and a same-generation different instance is rejected (`STALE_FENCE`). Different stream epoch is rejected (`CURSOR_RESET_REQUIRED`). This is **not an authorization credential**: expiry, process restart, takeover or recovered historical acquire responses require fresh server-side lease/fence validation before sync/ACK. No implicit polling, retry loop or second business state machine is provided.

Attachment file installation is separate and **not implemented in this lane**: derive stable safe filenames from message/attachment IDs, never overwrite a different file, verify an existing file before recording. Because file write and SQLite transaction cannot be atomic, crash after file save but before `recordReceived` requires a caller-managed directory/manifest scan to identify orphaned files, validate digest and restore their records safely. This module neither writes files nor claims this recovery exists. Errors use fixed `ImError` codes for request, attachment, conflicts, missing durable records and capacity failures; schema mismatch uses the existing `IM_SCHEMA_MISMATCH` error code. Do not log raw SQL, file paths, bodies, base64 or credentials.

Creation verifies SQLite `PRAGMA synchronous` is FULL or EXTRA and requires a file-backed main database; `:memory:` requires explicit `testOnlyMemory:true` and is exclusively for tests. The factory's complete signature is `createImJournal({db,centerId,agentId,testOnlyMemory?})`. The journal budget covers a 10 MiB base64 attachment plus maximally escaped legal text and metadata without truncation. The complete ACK signature (superseding the abbreviated form above) is `markAcked({messageIds,ackedThrough,streamEpoch,syncAckedThrough,localCursor,seqs})`: the last three fields come from trusted sync, persisted local state and the corresponding submitted records, not untrusted response data. Watermark regression, a watermark beyond the locally provable continuous ACK range (including previously ACKed rows bridged by this batch), and a watermark below the newly contiguous local cursor reject atomically. Legitimate out-of-order ACKs may leave cursor behind the largest submitted sequence. On Windows directory fsync may be unavailable/ignored: file-link recovery covers process crashes, not guaranteed power-loss durability across storage media.
