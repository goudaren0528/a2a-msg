### 做了什么

- `scripts/im-nana-provision.mjs`：只建全新绝对目录，schema 3 隔离中心 + 两个可配置显示名（默认 `nana-home` / `nana-office`）的合成身份、凭据、双向联系人、启用写入；产出 `center-config.json` 与 `host-a/nana.json`、`host-b/nana.json`。
- `src/nana/config.js` + `src/nana/session.js`：宿主无关会话适配层。`receive` 每次新租约、先 `ack_pending` 对账、`sync` 在 journal 落盘后才 ACK；`handoff` 从 journal 读队列并用独立 `session-state.json`（fsync + rename）推进游标；`send` 同 `clientMessageId` 幂等；`message`/`read` 查 `deliveredAt`/`readAt`。
- `scripts/im-nana-session.mjs`：`status|receive|handoff|send|message|read` 六子命令，JSON 输出，错误只给固定码。
- `examples/im-nana-roundtrip.mjs` + `tests/im-nana-*.test.js`：按 T1 §8 的独立中心进程 + 两个身份闭环，覆盖离线发送、落盘后 ACK、队列交接、重复投递、重启恢复、回复/已读、401/404、`LEASE_CONFLICT`。

### 还剩什么 / 需要跟进 Agent 确认

1. **适配层位置（需确认）**：T1 §9.1 第 3 条写的是 nanazi 侧 Python 适配层（`tools/ps_a2a.py` + `ps_store.ingest`），本任务工作目录限定 a2a-msg，故在 `src/nana/` 实现 Node 等价适配层。若 Nana 常驻会话要直接消费，需要宿主侧再接一层把 `handoff` 输出写进 `ps_store`。请确认这个取舍。
2. **已知产品缺陷（不在本包范围，未改）**：`src/im/mcp-adapter.js` 的 `defaultTransport` 只处理 `method/path/credential/binary`，丢弃 `body` 与 `headers`，导致该工厂在不注入 `transport` 时所有 POST（send/lease/ack）与带接收证明头的 `sync` 都失败（`INVALID_REQUEST`）。现有测试都注入 transport，所以未暴露。本包因此改用 `createImClient`（自带正确 HTTPS transport）+ 只读 GET 查询，未改 `src/im/`。建议另开修复。
3. **租约/身份模型**：按「每次 receive 新租约、单接收者」实现；多设备并行收、统一主体等 T1 §9.3 第 2 条问题未拍板，未做。
4. **未覆盖**：附件、7 天留存、AC-10/AC-23 契约、LAN/公网部署、开机自启。
5. **既有测试基线**：macOS 本机全量 `npm test` 有 762 个既有失败（`127.0.0.2/3` 别名、`/var` 符号链接），`tests/im-bootstrap.test.js` 等同样在基线失败；验收若在本机跑全量，请以「新增用例 + 基线对照」为准。
