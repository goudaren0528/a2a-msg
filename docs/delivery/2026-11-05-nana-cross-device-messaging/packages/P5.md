## 设计口径（实现前定稿）

- **发送**：`im_v1_send_file` 只挂在 stdio 入口（`src/im/mcp-stdio.js` + 新模块 `src/im/mcp-local-files.js`），不改 `src/im/mcp-adapter.js`（不在本包归属）。工具读本地文件后映射到既有 `im_v1_send`：
  - `path` 必须绝对、无 NUL；`lstat` + `O_NOFOLLOW` 打开；只接受普通文件、非符号链接；
  - 大小 `1..10485760` 字节：空文件 `INVALID_ATTACHMENT`，超限 `PAYLOAD_TOO_LARGE`；
  - 读取前后校验 `dev/ino/size/mtime`，读完自己算 SHA-256；变更/截断 → `INVALID_ATTACHMENT`；
  - 附件名默认取 basename，显式 `name`/`mime` 走既有契约校验；不返回原始字节，不读 URL；
  - 幂等沿用 `client.send`：同 `clientMessageId` + 同内容返回同一 `messageId`，内容变化 `IDEMPOTENCY_CONFLICT`。
- **接收**：沿用 P3 的 `saveAttachment`（独占落盘、SHA-256/大小校验、journal-before-ACK）。本包只补默认目录：
  - `nana.json` 的 `attachmentDirectory` 改为可选；缺省解析为 `~/Downloads/a2a-msg/<center-host>[_<port>]`（`os.homedir()`，不在 npx 缓存）；
  - 默认目录首次启动 `mkdir -p`（0700）；**显式配置**或 `--download-dir` 的目录必须已存在（不自动创建），缺失/不可写/损坏一律固定错误码且不 ACK；
  - `--download-dir <绝对路径>` 优先级：命令行 > `nana.json` > 默认。
- **失败语义**：目录不存在/不可写 → `INVALID_REQUEST`（启动 fail closed）或 `INVALID_ATTACHMENT`（运行中）；下载字节 hash/大小不符 → `INVALID_ATTACHMENT`；以上都不写 journal、不 ACK、不标已收，重试按 messageId 去重。
- **`bin/a2a-msg.mjs`**：当前基线不存在（属 P4），本包不改/不建；`--download-dir` 落在现有 `scripts/im-mcp.mjs`（P4 的 bin 后续转发同一参数）。见「交接」的机制问题。

AC-10 / AC-11 落点（都在 `tests/im-mcp-local-files.test.js`）：

- **AC-10**：`im_v1_send_file` 读本地 64 KiB 文件发送，发送结果只含 `{clientMessageId,messageId,acceptedAt,attachment:{name,mime,size,sha256}}`（不回显字节/暂存 base64）；接收端 `im_v1_sync` 与 `im_v1_attachment` 落盘到配置目录，`receipt.sha256`/`size` 与本地一致，文件字节逐字节相等，目录内无暂存残留。默认目录用例：`attachmentDirectory` 缺省、子进程 `HOME` 隔离时落盘到 `~/Downloads/a2a-msg/localhost_<port>`，启动即按需创建（0700），路径不含 `_npx`/`node_modules`；`--download-dir` 用例：显式覆盖优先于 `nana.json`，配置目录保持为空。
- **AC-11**：显式 `--download-dir` 不存在 → 启动退出码 1、stderr `{"error":{"code":"INVALID_REQUEST"}}`、stdout 为空；运行中删除目录 → `im_v1_sync` 返回 `INVALID_ATTACHMENT`，`im_v1_message.deliveredAt` 仍为 `null`；目录 `chmod 0500` → 同样 `INVALID_ATTACHMENT` 且未 ACK；恢复目录后同一 `messageId` 只交付一次、再 sync 返回 0 条、中心只有 1 条消息、目录只有 1 个文件。中心侧附件字节被篡改 → 固定码 `STORAGE_UNAVAILABLE`、未 ACK、目录为空，恢复后只交付一次。源文件侧：相对路径 `INVALID_REQUEST`、缺失/目录/符号链接/空文件/非法名 `INVALID_ATTACHMENT`、>10 MiB `PAYLOAD_TOO_LARGE`；同 key 同内容重发返回同一 `messageId`，同 key 不同内容 `IDEMPOTENCY_CONFLICT`，中心消息数不增加。

性能 / 安全自查（只看变更路径）：

- **性能**：`im_v1_send_file` 每次调用只读一个 ≤10 MiB 文件并复用既有 `identity()` + 一次 `POST /messages`，无循环网络、无 N+1、无定时器/watcher；接收路径与 P3 相同，单页 ≤100。临时内存上界约 10 MiB 文件 + 14 MiB base64，落在既有 `MAX_JSON`/`MAX_ATTACHMENT_BYTES` 内。
- **安全**：本地文件必须绝对路径、普通文件、非符号链接（`lstat` + `O_NOFOLLOW`），读取前后核对 `dev/ino/size/mtime`；错误只返回固定码，不含 OS 文本、路径内容或文件字节；发送结果不回显 base64；凭据仍只在 `Authorization`。默认目录用 `homedir()`，不写 npx/临时缓存；显式目录不自动创建，fail closed。
- **残余风险（交验收判断，不在本包扩范围）**：工具按宿主进程权限可读任意绝对路径文件（这是"发送本地文件"的固有语义），没有目录白名单；若宿主会执行不可信指令，应由宿主侧再限制可读范围。
