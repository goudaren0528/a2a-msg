## 机制问题

1. **派发基线写 `origin/main`，与本任务文件和线上部署线不符**
   - 现象：任务说明要求「执行开始时先 `git fetch origin`，以最新的 `origin/main` 为准」，但 `origin/main`（407254e）是 v1 team-mailbox，`src/im/config.js`、`scripts/im-center.mjs`、`src/im/join-page.js`、`src/im/mcp-http.js` 都不存在；这些文件与 VPS 上运行的 `db6ae65` 都在 `origin/feat/a2a-no-install`。工作区初始也被建在 `origin/main` 上，直接开工无从下手。
   - 触发条件：项目仓库默认分支（main）不是实现主线，nanazi 派发仍按默认分支生成 `base_ref: main`。
   - 影响范围：所有 a2a-msg IM 相关任务；本次已把任务分支重置到 `origin/feat/a2a-no-install` 才继续。
   - 复现步骤：`git ls-tree origin/main src/im` → 空；`git ls-tree origin/feat/a2a-no-install src/im` → 有；`git log -1 origin/feat/a2a-no-install` → `db6ae65`。
   - 初步归因：派发机制（默认分支/基线推导），非脚本偶发。
   - 建议修法：项目级登记「实现基线分支」，派发与运行记录用它生成 `base_ref`/`comparison`；或在任务行显式写 `base:feat/a2a-no-install` 并校验文件归属是否存在。
2. **授权「合并到 main」与实际主线不一致，导致交付只能停在 `branch-only`**
   - 现象：任务授权只允许「合并到 main」，但 main 没有 IM v2 代码；要合只能把 `feat/a2a-no-install` 整条线（70+ 提交）并进 main，超出本任务范围，且会让 main 与 v1 语义混在一起。
   - 触发条件：同 1，授权模板默认 main 为集成分支。
   - 影响范围：本任务无法按授权完成合并；线上部署的是任务分支归档，后续若从 feat 线重新部署会丢掉本改动。
   - 复现步骤：`git merge-base --is-ancestor origin/main origin/feat/a2a-no-install` → 非祖先；`git log --oneline origin/main..origin/feat/a2a-no-install | wc -l` → 70。
   - 初步归因：派发机制（授权目标推导），非开发执行问题。
   - 建议修法：授权合并目标应与「实现基线分支」一致；或在任务行点名允许合入的集成分支，避免 main/feature 线二选一时只能保守停在 `branch-only`。
