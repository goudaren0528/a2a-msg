## AC-BM5 具体断言与根因

### 失败断言

CI run `43011083105`（ubuntu-latest，2026-11-11 11:20–11:22）唯一新增失败：

```text
test at tests/im-registry-lock.test.js:152:1
✖ simultaneous first init from independent processes retains one coordination inode (84.240429ms)
  Error: first init result: unexpected IPC REGISTRY_DURABILITY_UNAVAILABLE
      at ChildProcess.onMessage (file:///home/runner/work/a2a-msg/a2a-msg/tests/im-registry-lock.test.js:47:19)
```

即 `expectMessage`（`tests/im-registry-lock.test.js:42-51`）在 `:47` 收到的 IPC 值不在该用例第 165 行允许集合
`['ready', 'REGISTRY_UNTRUSTED_PATH', 'REGISTRY_BUSY']` 内，直接 reject；第 168 行的 `assert.ok(results.some(…))` 因此没有再执行。

### 根因链（时序竞态，非合并冲突残留、非环境差异）

1. 两个独立进程从同一 barrier 同时做首次初始化。一个进程用 `openSync(path, O_CREAT|O_EXCL|O_RDWR|O_NOFOLLOW)` 赢得选举（`src/im/registry-lock.js:21`）；另一进程拿到 `EEXIST`，按 `src/im/registry-lock.js:39-45` 落入 `validate()` + `probe()`（`:56-73`），用只读连接对**刚刚出现、还是 0 字节**的 `coordination.sqlite` 执行 `PRAGMA`/读语句，期间持有 SQLite **SHARED** 锁。
2. 胜者在 `fsync`/`close` 后打开写连接，执行 `PRAGMA journal_mode=DELETE; PRAGMA busy_timeout=0; PRAGMA user_version=1`（`:29`）。`user_version=1` 要写数据库头，需要 EXCLUSIVE 锁；恰在败者读语句持有 SHARED 的瞬间，SQLite **立即**返回 `SQLITE_BUSY`，且**不调用 busy handler**（SQLite 为避免潜在死锁的既定行为，`busy_timeout` 对此无效——本机实测确认）。
3. init 的兜底 `catch`（`:39-45`）把任何既非 `EEXIST`、又非 `REGISTRY_*` 的错误统一映射成 `REGISTRY_DURABILITY_UNAVAILABLE`；fixture 只回传 `error.code`，测试便把它当成「意外 IPC」失败。

### 证据

- **同代码、重跑不复现（时序性）**：run `43014105544`（2026-11-11 11:42，main 上更晚的提交）ubuntu `tests 2850 / pass 2688 / fail 101`，该用例**通过**；同一提交的 run `43011083105` 为 `2687 / 102` 且该用例失败。
- **非合并冲突残留**：T100190 的合并树与 `feat` tip `8e9159c` 逐字节相同；`src/im/registry-lock.js`、`tests/im-registry-lock.test.js` 与 `master`（`b23dd26`）也一致，`f6e32d2` 是 master 的祖先。合并只带来更多并行测试文件（2765→2850），提高了该竞态的触发概率。
- **本机复现真实模块**：用仓库内 `createBackupRegistry` fork 两进程、16 并发做 400 组首初始化，命中 10 次 `REGISTRY_DURABILITY_UNAVAILABLE`；把兜底换到会带出底层错误的临时副本后，底层错误全部为
  `ERR_SQLITE_ERROR errcode=5 errstr="database is locked"`（`registry-lock.js:43` 的映射点）。
- **机制单独验证**：0 字节 `coordination.sqlite` 上，另一连接 `BEGIN` + 读后持 SHARED 时，写连接 `PRAGMA user_version=1` 返回 `errcode=5`；`PRAGMA journal_mode=DELETE` 与读 PRAGMA 不受影响；`PRAGMA busy_timeout=1000` 对该写**无效**；读连接释放后同一连接重试成功。

## 修复（AC-BM6）

`src/im/registry-lock.js`：只对首次初始化（O_EXCL 胜者）的初始化 PRAGMA 做**有界重试**——`performance.now() + 2000` 截止，遇 `busy()` 每 2ms 重试一次；其余错误立即抛出，继续走原来的 `REGISTRY_DURABILITY_UNAVAILABLE` 映射。理由：O_EXCL 已证明只有本进程可以初始化该 inode，此刻持锁的只可能是输掉选举、正在 probe 的瞬时读者；其余路径的 `busy_timeout=0` 与「争用快速失败」语义保持不变（`:82` 起的 `withLock` 未改）。

`tests/im-registry-lock.test.js`：新增确定性回归用例 `first init waits out a reader that probed the just-created inode`（`tests/fixtures/im-registry-lock/reader.js`）。用 `createRegistryLock(root, platform)` 已有的测试用 platform 注入口，在 `checkOpened`（原始 inode 已存在、SQLite 尚未写头部）处阻塞到子进程以只读事务真正持锁，再让初始化继续；子进程 500ms 后释放。修复前该用例在 35ms 内以 `REGISTRY_DURABILITY_UNAVAILABLE` 失败，修复后通过。**原有测试与断言一字未放宽**。

1. **依赖未收口就派发修复任务：T100194 的基线前提来自仍 `[~]` 的 T100190**

   - 影响范围：修复任务从未经核实的结论出发（本次靠重新拉取 CI 日志与复现才确认前提成立）。
   - 复现步骤：读 `plans/…md#T100194` 的 `dep:T100190` 与 `packages/T100190-P1.md` 的 `status: review`；对照派发摘要的「检查提醒」。

   - 建议修法：依赖任务至少到「验收完成」再派修复，或在派发里把基线结论标为「待核」并附证据路径。
