## 性能 / 安全自查（只看变更路径）

- 无 `setInterval`/`setTimeout` 常驻任务、无 watcher、无 SSE；所有网络请求只发生在工具调用内；进程由宿主管理，stdin 关闭或 `SIGINT`/`SIGTERM` 时关闭 journal 与在途请求。
- 每个请求一次 HTTPS 往返，沿用既有客户端语义（单页 `limit ≤ 100`）；响应有界：JSON ≤ 16 MiB、二进制 ≤ 10 MiB，30s socket 超时 + 30s deadline，超限 `PAYLOAD_TOO_LARGE`/`STORAGE_UNAVAILABLE`。
- TLS 校验链与主机名、不跟随重定向；CA 只从宿主进程环境（如 `NODE_EXTRA_CA_CERTS`）来，不接受工具参数；`Authorization` 只带凭据，凭据不进 body/错误/日志。
- 凭据文件要求普通文件、非符号链接、POSIX owner-only（`0600` 或更严；Windows 依赖 NTFS ACL，已在文档写明）；配置与 journal 目录也拒绝符号链接。
- journal 仍是既有 `createImJournal`（`foreign_keys=ON; synchronous=FULL`），本包未改 schema；`umask(0o077)` 保证新建文件只有本人可读。

### 做了什么

- `src/im/mcp-stdio.js`：把既有 `createImMcpAdapter` 挂到 stdio 宿主。`readNanaConfigFile` 复用 `src/nana/config.js` 的严格 schema（与 `scripts/im-nana-session.mjs` 共用一份 `nana.json`）；启动前校验 `attachmentDirectory`/journal 父目录存在且非符号链接，并同步读一次凭据（缺失或不安全即退出）；之后每个请求重新读 `credentialFile`，凭据轮换无需重启。自建校验 HTTPS transport，保留 `body`/`headers` 并限制响应大小——工厂自带的 `defaultTransport` 只适合只读 GET，会丢掉 POST body。
- `scripts/im-mcp.mjs`：`node scripts/im-mcp.mjs --config <nana.json>` 由宿主按需拉起，注册 16 个 `im_v1_*` 工具；stdout 只走 MCP 协议，错误走 stderr 固定错误码，`--help` 打印用法。
- `tests/im-mcp-stdio.test.js`：真实 MCP SDK 拉起 + 工具调用 + 空闲不联网 + 配置/凭据 fail closed 三条用例。
- 文档：`docs/im-mcp-adapter.md`（stdio 入口、配置、凭据、TLS、无轮询、宿主配置示例）、`docs/im-nana-adapter.md`（同一份 `nana.json`、租约冲突提示）、`docs/client.md`（顶部区分 LAN bridge 与 IM v1 两条入口）。

### 还剩什么 / 需要跟进 Agent 确认

1. **`src/im/mcp-adapter.js` 的 `defaultTransport` 仍是只读实现**（丢 `body`/`headers`，无注入 transport 时 `ensure_conversation`/`send`/`acquire_lease`/`sync`/`ack_pending`/`read` 都会失败）。该文件不在 P3 文件归属（在 P2 的归属里），本包未改，只在 stdio 入口注入自己的 transport。建议 P2 顺手修，或在 P3 之后单开修复。
2. **未挂进任何真实宿主**：AC-7 只要求用真实 MCP SDK 拉起（已做）。真正把 `scripts/im-mcp.mjs` 写进 Nana / 其他宿主的配置、以及 `npx` 形态属于 P4/P6；本包给出示例配置但不改宿主文件。
3. **附件工具可用但下载目录未做默认值**：`attachmentDirectory` 必须是已存在的绝对目录（沿用 `nana.json` 语义）；npx 场景的默认下载目录与 `--download-dir` 属 P5。
4. **租约模型未变**：同一身份同一时刻只能一个接收者；MCP 入口与 `im-nana-session.mjs receive` 同时跑会 `LEASE_CONFLICT`，已在文档写明。
