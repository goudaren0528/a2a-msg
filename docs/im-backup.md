# Local IM backup and verification (isolated runner)

`createImBackup({ db, authority, clock, toolVersion, backupTimeBudgetMs, backupRate, durability })` returns async `backup({ destinationPath, approvalId, sourceId, adminContext })`, sync `verify({ backupPath, manifestPath })`, `status()` and async `drain()`. The caller passes `adminContext` independently from IDs, only within an already authenticated/approved scope (for example `{ adminSecret }` for `createAdminAuthority`); it is never serialized. `approvalId` and `sourceId` are **metadata, not authentication**. The authority must synchronously return literal `true` before any output. Do not provide secret material as metadata.

Node 24 `node:sqlite` online backup creates a consistent SQLite snapshot; the unsupported synchronous `VACUUM INTO` fallback is removed (`BACKUP_UNSUPPORTED` if native backup is unavailable). Default `backupRate=256` pages/step (configurable 1–100000); 8 MiB local benchmark is in the test suite. An external WAL writer can repeatedly restart the native operation. Default monotonic `backupTimeBudgetMs=30000` (1–300000) ensures **no publication on timeout**, not that synchronous integrity checks, hashes, fsyncs or native callbacks always return within the budget. Native backup has no cancellation; `BACKUP_BUSY` leaves at most one native operation running per source DB connection, even across runners. `status().nativeInFlight` indicates this state and `await drain()` waits for settlement, not publication. Stop external writers before retrying if progress is impossible.

Snapshot temporary DB is closed by SQLite native backup, explicitly fsynced before inspection and publication; integrity/foreign-key/schema checks and bounded-memory streaming SHA-256 precede manifest creation. Manifest is fsynced; DB hard link and then manifest hard link publish with no-replace semantics, with directory fsync after each. **Strict** durability (default) fails closed (`BACKUP_DURABILITY_UNAVAILABLE`) if directory sync is unavailable. For platforms such as Windows where directory handles may reject fsync, opt in explicitly to `durability: 'best-effort'`; successful results then say `durability: 'degraded'`, **not** durable. Do not use degraded results as equivalent crash-safe evidence. Pending files and partial pairs are not usable evidence. Hard links require a trusted local filesystem and protected destination directory; this primitive is not hardened for adversarial concurrent filesystem mutation.

`verify()` is a **content verifier**: it checks hash, SQLite integrity, foreign keys and IM schema. It **does not prove manifest origin or that the backup belongs to the current source database**; provenance is a separate responsibility of a future migration gate. An attacker able to rewrite DB and manifest can recompute the hash. `.pending` paths are rejected; a verified completed pair alone is not sufficient migration authorization.

Manifest fields: `backupId`, `sourceId`, `schemaVersion`, `schemaChecksum`, `toolVersion`, `completedAt`, `fileHash`, verification booleans and `approvalId`. The backup contains sensitive message and credential data; independently protect and encrypt it. No admin context is included. Failure codes: `BACKUP_AUTH_DENIED`, `BACKUP_TARGET_EXISTS`, `BACKUP_VERIFY_FAILED`, `BACKUP_BUSY`, `BACKUP_UNSUPPORTED`, `BACKUP_DURABILITY_UNAVAILABLE`, `BACKUP_FAILED` (including ENOSPC and permissions). This runner is not deployment, migration, restore or disaster-recovery readiness proof. Recovery requires separate approved, isolated restore rehearsal; never overwrite a live DB automatically.
